# Checkpoint 1 findings — does ingestion measurably affect query latency?

Per `research-plan/rupali_ingestion_aware_scheduler_paper_plan.md`'s Week 2
go/no-go gate and `research-plan/scheduler_scope_and_infra_notes.md`'s staged
testing approach. Raw data: `results/checkpoint1_timing.csv`. Harness:
`scripts/query_timing_harness.py`.

## TL;DR

- **Yes, ingestion affects query latency — two different mechanisms, two
  different confidence levels.**
- **Data volume** (more ingested data registered and in scope for the
  query's scan): latency roughly **doubled** (364ms → 553ms mean). Clean,
  unconfounded result, high confidence.
- **Pure concurrent writing** (a producer actively pushing bytes into MinIO
  while the query runs, even when its new files aren't yet visible to the
  query): latency rose **~70-80ms** on a ~330-420ms baseline in a properly
  controlled test, but the statistical check says this could plausibly be
  noise about 1 time in 10 (p ≈ 0.09-0.13) — a real trend, not yet proof.
- **Verdict: conditional go** on Checkpoint 1 — proceed to Week 3, but treat
  the two mechanisms as separate and don't oversell the concurrency finding
  as settled until it's retested with more repetitions.

## Metrics — what they mean here

Every condition below is summarized by six numbers, computed from n repeated
runs of the *identical* query:

| Metric | Meaning | Why it matters for this test |
|---|---|---|
| **n** | Number of times the query was run under that condition | More runs = less luck-of-the-draw in the summary numbers. 10-15 here; genuinely low for how noisy the box turned out to be (see stdev). |
| **mean** | Average runtime across the n runs | Easiest to compare at a glance, but easily dragged around by a couple of slow outliers — this data has those. |
| **median** | The middle value if all n runs are sorted | More robust to outliers than the mean. When mean and median diverge a lot (they do here — e.g. 418ms mean vs 329ms median for `no_burst_before`), that itself is a signal: a right-skewed distribution with occasional slow runs, not a uniformly-shifted one. |
| **stdev** | Standard deviation — how spread out the runs are around the mean | The real story in this dataset. Stdev of 150-180ms on a ~350-500ms query means run-to-run noise is comparable in size to the effects we're trying to detect — this is *why* a permutation test was needed instead of just eyeballing the means. |
| **min / max** | Fastest and slowest single run in the block | Shows the actual range, including outliers stdev only hints at. Several blocks have one run at 2-3x the others. |
| **permutation-test p-value** | Probability of seeing a difference this large (or larger) between two groups **purely by random chance**, if ingestion actually had zero effect | Standard significance check, computed by reshuffling the timing values between the two conditions 20,000 times and counting how often a random reshuffle produces as big a gap as the real data did. Conventionally, p < 0.05 is treated as "probably not chance." Here: p ≈ 0.09 (mean) and p ≈ 0.13 (median) for the concurrency effect — **below that bar**, meaning it's suggestive but not something to state as proven in the paper yet. |

## What was tested

One fixed query, repeated many times, timed end-to-end (query submit to
result fetch complete), against Trino on the Ryzen box:

```sql
SELECT
    count(*) AS n_orders,
    sum(CAST(json_extract_scalar(payload_json, '$.o_totalprice') AS DOUBLE)) AS total_price
FROM hive.events.raw_events
WHERE schema_id = 'tpch_orders_v1'
```

This is a full-table-scan aggregation (no partition filter) over
`hive.events.raw_events` — a Hive-partitioned external table
(`year/month/day/hour/source`) backed by Parquet files in the
`lakehouse-events` MinIO bucket. `schema_id` is a row-level filter, not a
partition column, so every registered partition's files get opened and
scanned regardless of which dataset the query logically wants.

**Environment:** Trino/MinIO/Hive-Metastore stack on the Ryzen box
(`YOUR_TRINO_HOST`), queried from a separate machine over Tailscale. Ingestion
load generated by the same local Kafka + Java ingestion service used in the
phase-0 pipeline (`adaptive-data-lake-producer`, `pipeline_tpch` branch),
writing to the same Ryzen-box MinIO. No other load on either machine during
testing, as far as observable.

## Two things this session tried to isolate

1. **Does registering more ingested data into the scan path slow the query
   down** — regardless of whether anything is actively writing at query
   time?
2. **Does an actively-writing producer contend for shared resources**
   (network, MinIO CPU/disk) with a concurrent read — even when the new
   data it's writing isn't yet visible to the query (unregistered
   partition)?

These turned out to require different experimental designs, and the first
attempt at (2) was confounded — see "First pass (confounded)" below before
the corrected design.

## First pass (confounded) — kept for the record

| Condition | n | mean | median | stdev | min | max |
|---|--:|--:|--:|--:|--:|--:|
| `none` (clean baseline) | 10 | 364.0ms | 347.2ms | 55.1 | 331.7 | 518.0 |
| `heavy_burst` (banking, unsynced) | 10 | 328.0ms | 325.2ms | 17.5 | 307.3 | 364.7 |
| `sync_only_no_burst` (banking partition registered, no active write) | 10 | 553.5ms | 522.2ms | 171.2 | 296.3 | 890.0 |
| `heavy_burst_synced` (fresh tpch-lineitem burst, active + synced) | 10 | 439.1ms | 401.7ms | 148.1 | 299.3 | 697.8 |

`sync_only_no_burst` ran before `heavy_burst_synced` in wall-clock time, and
each condition changed the registered scan scope (more partitions got
synced in between). So the drop from 553.5ms to 439.1ms between those two
conditions is not evidence that concurrent writing is *faster* than static
data — it's confounded by (a) growing scope between conditions and (b) the
second scan likely hitting warmer OS/MinIO caches for files the first scan
had just read. Question (1) above got a clean-enough answer from `none` vs
`sync_only_no_burst` (a real, large effect); question (2) did not.

## Corrected design — before/during/after (ABA), frozen scope

To isolate question (2) cleanly:

- **Freeze scan scope**: no `sync_partition_metadata` calls during this test,
  so every trial in all three blocks scans the exact same registered
  partitions. A concurrent burst's new files land in an unregistered
  partition and are invisible to the query — this isolates *physical*
  resource contention (network/MinIO/CPU) from the *data-volume* effect
  already captured above.
- **ABA blocks, not a single before/after pair**: no-burst measured both
  *before* and *after* the burst window, not just before. If drift (caching,
  thermal, anything time-dependent) were contaminating the comparison, the
  "before" and "after" blocks should differ from each other — they're a
  built-in consistency check, not just a control for the burst block.
- **True per-trial randomization was not achievable**: the producer
  (`banking_producer.main`) streams a fixed CSV start-to-finish with no
  pause/resume control, so a burst can't be toggled on/off mid-stream to
  interleave individual trials. ABA block order was the best available
  substitute given that constraint — noted here rather than glossed over.
- 15 trials per block, 0.3s pacing between trials, same query throughout.
- Burst source: `banking_transaction_v1` (fresh — past its 60-minute
  ingestion-service dedup window from the earlier test — see
  `DeduplicationStore.java`), 550,000 rows, ~100s streaming window, confirmed
  still actively sending (78,000/550,000) partway through the `burst_during`
  block.

| Block | Window (UTC) | n | mean | median | stdev | min | max |
|---|---|--:|--:|--:|--:|--:|--:|
| `no_burst_before` | 13:42:17–13:42:28 | 15 | 418.2ms | 328.9ms | 180.3 | 293.7 | 893.0 |
| `burst_during` | 13:43:13–13:43:25 | 15 | 488.0ms | 409.4ms | 179.9 | 276.1 | 769.7 |
| `no_burst_after` | 13:46:15–13:46:25 | 15 | 412.0ms | 330.1ms | 139.2 | 291.3 | 687.7 |

**Before ≈ after** (mean 418.2 vs 412.0; median 328.9 vs 330.1) — the two
no-burst blocks agree closely despite being ~4 minutes apart, so time-drift
/ caching is not a major confound here.

**Burst_during sits above both**: +70ms mean, +80ms median relative to the
combined no-burst blocks (n=30, mean 415.1ms, median 329.5ms).

**Significance check** (one-sided permutation test, 20,000 resamples,
`burst_during` vs pooled `no_burst_before`+`no_burst_after`):

- mean difference (+72.9ms): p ≈ 0.088
- median difference (+79.9ms): p ≈ 0.127

Not conventionally significant at p<0.05 — suggestive, not conclusive, at
n=15 per block against this much run-to-run variance (stdev ~150-180ms on a
~330-500ms query, driven by a heavy right tail: a handful of 700-900ms
outliers in every block, `none` block included).

## Interpretation

1. **Data-volume effect (question 1) is real and large.** Registering more
   ingested data into the query's scan path roughly doubled mean latency
   (364ms → 553ms) and tripled the spread, in the very first, unconfounded
   comparison. This alone is a legitimate, repeatable ingestion effect.
2. **Pure concurrent-write contention (question 2) shows a consistent
   directional signal — burst_during higher than both flanking baselines,
   with internal consistency confirmed by before≈after — but is not yet
   statistically conclusive at this sample size.** The effect (~70-80ms on a
   ~330-420ms median) is real enough to keep pursuing, not strong enough to
   claim as proven from one ABA pass.
3. **Variance is the dominant challenge, not the mean.** Every block,
   including totally quiescent ones, has occasional 2x-outliers. Any Week
   3+ experiment design needs enough repetitions (and probably p95/p99
   reporting, not just mean/median) to separate real tail effects from this
   baseline noise floor.

## Conclusion

**Checkpoint 1 verdict: conditional go.** The plan's Week 2 gate question —
"does ingestion measurably affect query latency?" — gets a qualified yes,
made of two separable answers rather than one:

1. **Data volume: proven.** A query that has to scan more registered
   ingested data is slower — 364ms → 553ms mean, tripled variance — in a
   clean, unconfounded comparison. No caveats needed here; this is solid
   enough to build on.
2. **Concurrent writing alone: plausible, not yet proven.** Isolating pure
   resource contention (same scan scope, burst's writes invisible to the
   query) via a before/during/after design showed a consistent ~70-80ms
   uplift during the burst, with the two no-burst blocks agreeing closely
   with each other (418ms vs 412ms mean) — so the uplift isn't explained by
   drift or caching. But at n=15 per block against ~150-180ms of run-to-run
   noise, the permutation test puts this at roughly 1-in-10 odds of being
   chance (p ≈ 0.09-0.13), not the conventional 1-in-20 bar. Directionally
   real, not yet citable as a confirmed result.

**What this means practically:**

- It's justified to proceed to Week 3 (query classes, SLA rules, baselines,
  the prediction dataset) — the premise ingestion affects performance is
  supported, not in doubt.
- Two things carry forward as requirements for the Week 3+ harness, not as
  loose ends to forget about:
  - More repetitions per condition (and ideally a rate-limited/steady-state
    producer instead of one-shot CSV replay, so concurrent-write windows can
    run long enough for a properly randomized, not just ABA-ordered, design)
    before the concurrency effect can be written up as confirmed rather than
    a trend.
  - Data-volume growth and concurrent-write contention are mechanistically
    different and have very different effect sizes (a ~190ms shift vs a
    ~75ms shift here) — the scheduler's features and the paper's framing
    should keep them as separate signals, not one undifferentiated
    "ingestion load" variable.
