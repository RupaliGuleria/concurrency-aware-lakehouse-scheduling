Why the same query took 19× longer under load

A single-node Trino experiment on query scheduling and admission control — what helped, and where it fell short.

Rupali Guleria·Independent Researcher

Picture a retail company on its biggest sale day of the year. Orders are pouring in, and a live dashboard keeps stalling. The usual explanation: too much new data coming in at once.

That explanation makes sense. But on the real system tested here, it turned out to be wrong.

Same query, same data, same machine. The only thing that changed was how many other queries were running at the same moment — which is exactly what a sale-day dashboard looks like: everyone refreshing together, not one big delivery of new data arriving at once.

But isn't it the incoming data?

Trino is the kind of engine behind that dashboard: it answers questions over data stored separately from the engine itself, often while new data is still being written in. The obvious fix for a slow dashboard is a scheduler that watches how much data is coming in and reorders queries around it. That was the starting plan for this project too — until it got tested.

A real Trino deployment ran the same kind of queries a dashboard asks — lookups, totals, joins — while a separate stream of data was fed in at different speeds, from none to heavy. Four separate tests, run at different points in the project, all landed on the same answer.

The incoming data wasn't the bottleneck. Not here, not at this scale. A scheduler built around it would have solved the wrong problem.

Someone has to decide who goes first

Here's what the crowding actually means for the dashboard: a pile of queries — revenue by hour, stock by warehouse, whatever's being asked right now — all want to run at once, but the machine can only run a few well at a time. Something has to decide which ones go first, which wait, and which might not make it in time at all. That decision-maker is called a scheduler. Each query in this study also has a deadline — the time it's supposed to finish by for its answer to still be useful — and the scheduler's whole job is choosing an order that gets as many queries across their deadline as possible.

Teaching the scheduler to notice the crowd

The simplest rule is called least slack. Slack is how much spare time a query has left before its deadline, once you subtract how long it's expected to take — a query with little slack is close to running out of time and should go first. The original version of this rule always guessed how long a query would take assuming the system was idle, a best-case guess. The rebuilt version checks how busy the system actually is right now instead, the way a delivery app updates your ETA once it sees real traffic instead of assuming empty roads.

That one change altered real decisions: the busy-aware version picked a different running order than the idle-assuming one in 488 out of 1,000 simulated batches. A second version goes further, using dynamic programming to compute the best possible order under those same estimates and the study's priority rules — not a rule of thumb, the provably best order given what it knows.

The bouncer at the door

Past a certain number of simultaneous queries, no amount of clever reordering helps. There simply isn't enough machine to go around, and every scheduler tested — including the mathematically optimal one — eventually hit 0% success at high enough load. Shuffling the line doesn't help when the room is already full.

The more useful response, the paper argues, isn't a smarter line. It's a door.

Before admitting a new query, check whether letting it in would still leave everything already admitted with a fair shot at its deadline. If not, that query waits — it isn't dropped, just run later, after the ones already let in.

This is the paper's admission control mechanism: a feasibility check at the door, not a smarter queue inside the room.

Tested live — and where it fell short

A simulation proving this works is one kind of evidence. The stronger kind is watching it hold up against a real, running system under real concurrent load.

In the moderate-concurrency live test — the busiest condition actually run live, rather than only simulated — the admission system recognized it was overloaded and deferred most new arrivals. But even among the queries it let through, success fell well short of its own target:

82.5%
of arrivals deferred, live, once the system judged itself overloaded (moderate-concurrency test)
33.3%
success rate among the queries it still let in — same test, versus an 80% target

In every other live condition tested, admitted queries beat the blended average — including the deliberately deferred ones, scored honestly as ordinary misses once they finally ran last. This one case is reported plainly rather than smoothed over: the mechanism's confidence in itself didn't match reality here.

The likely cause: its predictions are built from measurements taken in short rounds, while this test ran under continuous background load — a denser kind of busy than the calibration data expected. A direct check of prediction error confirms it: at this exact condition, the error rate was roughly four times higher than everywhere else tested.

Why this matters past one dashboard

The specific numbers here come from one machine, one workload, three coarse levels of "how busy." They aren't a universal law. What travels further is the method: a popular assumption, tested directly before anything was built around it, and a result that overturned the premise the project started with.

That pattern — the moment a system is suddenly asked for everything, by everyone, at once — isn't specific to lakehouses. It's payday in a banking app, checkout during a flash sale, a results page the morning grades come out. The systems that stay calm through those moments usually aren't the ones that got smarter about ordering the line. They're the ones that learned when to say, politely, not yet.
