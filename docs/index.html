Checkpoint 1 · Week 2 go/no-go gate

Does ingestion measurably affect query latency?

Two mechanisms tested against the same Trino query, timed end-to-end: registering more ingested data into a scan, and a producer actively writing while a query runs. They behave differently — and carry different confidence.

Ryzen box · Trino / MinIO / Hive Metastore 2026‑08‑19 n = 87 runs scripts/query_timing_harness.py
01

Metrics glossary

Read this first — every chart and table below is built from these six numbers, computed per condition from n repeated runs of the identical query.

MetricMeaningWhy it matters here
n Number of times the query ran under that condition. 10–15 here — genuinely low for how noisy the box turned out to be (see stdev).
mean Average runtime across the n runs. Easiest to compare at a glance, but easily dragged around by a couple of slow outliers — this data has those.
median The middle value once all n runs are sorted. More robust to outliers than the mean. When mean and median diverge a lot (418ms vs 329ms for no_burst_before), that's itself a signal: a right-skewed distribution with occasional slow runs, not a uniform shift.
stdev Standard deviation — how spread out the runs are around the mean. The real story in this dataset. 150–180ms of spread on a ~350–500ms query means run-to-run noise is comparable in size to the effects being measured — this is why a permutation test was needed instead of just eyeballing the means.
min / max Fastest and slowest single run in the block. Shows the actual range, including outliers stdev only hints at. Several blocks have one run at 2–3x the others.
permutation‑test p‑value Probability of seeing a difference this large purely by chance, if the condition actually had zero effect. Computed by reshuffling timing values between two conditions 20,000 times. p<0.05 is the conventional "probably not chance" bar. Here: p ≈ 0.09 (mean) and p ≈ 0.13 (median) for the concurrency effect — below that bar, so suggestive rather than proven.

03

What was tested

One fixed query, repeated many times, timed submit‑to‑fetch‑complete, against Trino on the Ryzen box (YOUR_TRINO_HOST), queried over Tailscale.

SELECT
    count(*) AS n_orders,
    sum(CAST(json_extract_scalar(payload_json, '$.o_totalprice') AS DOUBLE)) AS total_price
FROM hive.events.raw_events
WHERE schema_id = 'tpch_orders_v1'
  • Table shape Hive-partitioned external table (year/month/day/hour/source) over Parquet in the lakehouse-events MinIO bucket.
  • Why it's slow No partition filter — schema_id is a row-level predicate, so every registered partition's files get opened regardless of which dataset the query wants.
  • Ingestion load Local Kafka + Java ingestion service (adaptive-data-lake-producer, pipeline_tpch branch) writing to the same Ryzen-box MinIO.
  • Isolation No other observable load on either machine during testing.
Two questions needed different experimental designs to isolate cleanly: (1) does registering more ingested data slow the scan, regardless of active writing? (2) does an actively-writing producer contend for shared resources even when its new files aren't yet visible to the query? The first attempt at (2) was confounded — see the note below the data‑volume chart.
04

The harness

Every row in the timing data comes from one script: scripts/query_timing_harness.py. It is deliberately a dumb stopwatch loop — the experimental design (ABA blocking, frozen scan scope, when to trigger the burst) lives in how it's invoked, not in the script itself.

  • Fixed query Runs the exact same SQL every time via Trino's Python client — only the --condition label changes between invocations, so timing differences can't be attributed to a different query.
  • Precise timing Wraps execute() + fetchall() in time.perf_counter(), recording wall-clock start/end plus elapsed runtime_ms. A failed run is caught and logged with its error text rather than crashing the batch.
  • Condition tagging --condition is a free-text label supplied by the caller (none, heavy_burst, …) — the harness doesn't infer it, so correctness depends on running it at the right moment relative to the ingestion producer.
  • Durable, incremental output Appends to results/checkpoint1_timing.csv and flush()es after every row, so a mid-run crash never loses already-completed timings.
  • Paced runs A configurable --sleep gap (default 1s) between queries, each row keyed by a unique run_id.

      07
      
Interpretation & conclusion

    


    

      
      

        
Data-volume effect: proven.

        
Registering more ingested data into the scan path roughly doubled mean latency (364ms → 553ms) and tripled the spread, in the very first, unconfounded comparison. No caveats needed — solid enough to build on.

      

    

    

      
      

        
Concurrent-write contention: plausible, not yet proven.

        
burst_during sits above both flanking baselines, with internal consistency confirmed by before≈after — but it isn't yet statistically conclusive at n=15 per block. The effect (~70–80ms on a ~330–420ms median) is real enough to keep pursuing, not strong enough to claim as settled from one ABA pass.

      

    

    

      
      

        
Variance is the dominant challenge, not the mean.

        
Every block, including totally quiescent ones, has occasional 2x outliers. Week 3+ experiment design needs enough repetitions — and probably p95/p99 reporting, not just mean/median — to separate real tail effects from this baseline noise floor.

      

    


    

      Verdict: conditional go. It's justified to proceed to Week 3 (query classes, SLA rules, baselines, the prediction dataset) — the premise that ingestion affects performance is supported, not in doubt. Two things carry forward as requirements for the Week 3+ harness, not loose ends: more repetitions per condition (ideally a rate-limited/steady-state producer instead of one-shot CSV replay, so concurrent-write windows can support a properly randomized design) before the concurrency effect is citable as confirmed; and keeping data-volume growth and concurrent-write contention as separate signals — a ~190ms shift vs a ~75ms shift, mechanistically different effect sizes that a blended "ingestion load" variable would erase.
